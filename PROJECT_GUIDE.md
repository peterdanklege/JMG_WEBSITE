# JMG Website — Project Guide (for AI assistants / developers)

This file exists so any AI coding assistant (Claude Code, Cursor, Copilot, etc.) or
human developer can quickly understand what this project is, how to edit it safely,
and how to redeploy it. Read this before making changes.

## What this is

A static marketing website (React + Vite) for JMG Web Development. It was
originally built on the Base44 platform, but **all Base44 dependencies have been
removed**. It is now a plain, framework-agnostic static site: build it, and you
get pure HTML/CSS/JS with no backend dependency.

There is no database, no server-side code, and no user authentication.
The only "dynamic" behavior is the contact form, which submits directly to
Web3Forms (a third-party form API) from the browser — no backend of ours involved.

## Two folders — do not confuse them

- **Source code** (`src/`, `package.json`, `vite.config.js`, etc.) — this is what
  you edit. Human-readable React components, plain CSS, etc.
- **`dist/`** — this is a *build output*, generated by running `npm run build`.
  It is minified/bundled JavaScript and is NOT meant to be hand-edited. If someone
  hands you a folder that is only `dist/` (no `src/`, no `package.json`), that is a
  **deploy-ready artifact, not source code** — there is nothing editable in it.
  Always make changes in the source project, then rebuild.

## Requirements

- Node.js 18+ and npm

## Setup

```bash
npm install
```

## Local development

```bash
npm run dev
```

Runs a local dev server (Vite) with hot reload, typically at `http://localhost:5173`.

## Building for production

```bash
npm run build
```

Outputs a fresh `dist/` folder containing the deployable static site. This is what
gets uploaded to a static host (currently deployed on Vercel).


## Routes

Defined in `src/App.jsx`:

- `/` → Home
- `/pricing` → Pricing
- `/contact` → Contact
- `/portfolio` → Portfolio (case studies)
- anything else → 404 page (`src/lib/PageNotFound.jsx`)

To add a new page: create a component in `src/pages/`, then add a `<Route>` for it
inside `src/App.jsx`, inside the `<Layout />`-wrapped route group (so it gets the
navbar/footer).

## Portfolio Page (`src/pages/Portfolio.jsx`)

The Portfolio page showcases completed client websites as case studies. It is
self-contained — no external CMS or API. All project data lives in a single
`PROJECTS` array at the top of `Portfolio.jsx`.

### Adding a new project

1. Open `src/pages/Portfolio.jsx`
2. Add a new object to the `PROJECTS` array at the top of the file. Copy an
   existing entry and update every field. The full schema is:

```js
{
    id: 'unique-slug',           // kebab-case, used as React key
    name: 'Client Name',         // displayed as heading
    tagline: 'Short descriptor', // one line under the name
    category: 'Local Business',  // shown as the tag pill
    year: '2025',                // displayed on card + modal
    accentClass: 'accent-green', // controls hover border colour:
                                 //   'accent-green' | 'accent-orange'
                                 //   'accent-purple' | 'accent-lime'
    accentColor: 'var(--green)', // CSS value — used in the modal header border
                                 // and section number highlights
    tags: ['React', 'Vite'],     // tech tags shown on card & modal
    liveUrl: 'https://...',      // set to null if not yet live; shows a
                                 // "View Live Site" button in the modal when set
    description: '...',          // 2–3 sentence overview paragraph
    challenge: '...',            // what problem the client had
    solution: '...',             // what you built and why
    features: [                  // bullet list of key features (aim for 8–12)
        'Feature one',
        'Feature two',
    ],
    pages: ['Home', 'About'],    // page names shown as pills in the modal header
    mockupColors: [              // 3 hex colours used to generate the browser
        '#1B2B4B',               // mockup graphic inside the card:
        '#3DBCB8',               //   [0] = dark/nav background
        '#1B6CA8',               //   [1] = accent/button colour
    ],                           //   [2] = hero gradient end colour
}
```

3. No other files need to change — the grid, modal, and stats strip all
   generate dynamically from the `PROJECTS` array.
4. Update the stats strip values (clients launched, etc.) manually — they are
   hardcoded JSX in the `Portfolio` component's stats strip section.

### CSS

All Portfolio-specific styles are appended at the bottom of
`src/styles/site.css` under the `/* PORTFOLIO PAGE */` comment block. The
component uses existing site design tokens (`--green`, `--orange`, `--surface-1`,
`--font-heading`, `.reveal`, `.overline`, etc.) so it naturally matches the rest
of the site without any extra configuration.

### Browser Mockup graphic

Each project card contains a CSS-only `<BrowserMockup>` component that
simulates what the client's website looks like. It accepts a `colors` array
(3 hex strings) and generates a simplified nav → hero → cards → footer layout
in those colours. It is purely decorative — replace it with a real screenshot
`<img>` if you have one by swapping the `<BrowserMockup>` in `ProjectCard` with
an `<img src={project.screenshot} alt="..." className="portfolio-card-img" />`.

### "Coming Soon" placeholder card

The last card in the grid is a static placeholder inviting new clients. It will
automatically move to the end as more `PROJECTS` entries are added (it is
rendered after the `.map()` call). Remove it once you have enough real projects
to fill the grid.

## The `@/` import alias

Imports like `import X from '@/components/...'` resolve to `src/`. This is
configured directly in `vite.config.js` under `resolve.alias`. **Do not remove
that alias config** — if it disappears, every `@/` import in the project breaks.

## Contact form (Web3Forms)

`src/pages/Contact.jsx` submits form data using `src/lib/web3forms.js`, which
posts directly to Web3Forms' public API endpoint using a public access key
embedded in the code. This requires no backend — Web3Forms emails the
submission to the site owner directly. If the access key ever needs to change
(e.g. new Web3Forms account), it's set inside `src/lib/web3forms.js`.

## Things to NOT reintroduce

- **Do not add Base44 back** (`@base44/sdk`, `@base44/vite-plugin`, or any
  `base44Client` import). It was deliberately and fully removed so this site can
  be hosted anywhere for free as a static site, with no backend dependency or
  monthly platform fee.
- Do not add server-side code (API routes, databases) unless the hosting plan
  changes — this project is designed to be a zero-backend static site.
- Don't use `localStorage`/`sessionStorage`-dependent features if this is ever
  embedded in restrictive sandboxed contexts (not required for normal hosting,
  just a portability note).

## Deployment

Currently deployed on **Vercel**, connected to the custom domain via GoDaddy DNS
(A record for the apex domain, CNAME for `www`). To redeploy after making
changes:

1. Make your edits in `src/`
2. Run `npm run build`
3. Upload the new `dist/` folder to Vercel (via dashboard drag-and-drop, or via
   Vercel CLI / Git integration if that's been set up)

## Changelog

### v3.3 — Site-wide dot grid, stronger glow, drag fix at fractional screen scaling
- **Dot grid is now a fixed, site-wide background** on every page (mounted once in `Layout.jsx` as `.site-bg`,
  `z-index: -1`). Full-width sections that used solid backgrounds (`.physics-section`, `.home-contact`,
  `.portfolio-hero`, `.portfolio-stats-strip`, `.portfolio-grid-section`) were made transparent or semi-transparent
  so the grid shows through. If you add a new full-width section, avoid a solid `background` or the grid will be hidden.
  Cards/modals keep solid backgrounds for readability. The hero keeps a soft scrim (`.hero::before`).
- **Stronger hover glow:** bigger radius, brighter dots, soft halo. With `prefers-reduced-motion` the hover glow
  still works but the ambient wave and ripples are off.
- **Bug fix — physics blocks couldn't be grabbed on many PCs.** Matter.js reads the screen scale with
  `parseInt`, so Windows display scaling of 125% / 150% (devicePixelRatio 1.25 / 1.5) became 1 and the pointer was
  offset 25–50%. `PhysicsSection.jsx` now sets `mouse.pixelRatio` itself (and on resize). Verified at 100/125/150/200%.

### v3.2 — Interactive hero dot grid
- **New: `src/components/site/DotGrid.jsx`** — a canvas dot matrix behind the hero. Dots swell and shift
  through the brand colours near the cursor, leave a fading trail, ripple as you move, and send a big
  ripple on click/tap. A faint ambient wave keeps it alive. Pointer events are listened for on `window`,
  so hero buttons and links stay fully clickable.
- **Performance:** loaded with `React.lazy` as its own ~2 KB chunk (never blocks first paint); only animates
  while the hero is on screen and the tab is visible; devicePixelRatio capped at 2. Respects
  `prefers-reduced-motion` (static dots) and is skipped entirely on data-saver / very low-memory devices.
- **Static fallback + readability:** `.hero-bg-static` (pure CSS dots) shows instantly and stays if the canvas
  doesn't load. `.hero-bg-overlay` darkens the centre behind the headline/CTAs and fades into the next section.
- **Tuning:** spacing `gap` (30px, 24px on mobile), influence radius `R` (190) and dot sizes are at the top of
  the `draw` function in `DotGrid.jsx`. Overlay strength is in `.hero-bg-overlay` in `site.css`.

### v3.1 — Carousel art, more blocks, drag fix
- **Carousel illustrations.** Each "Features we can build" card now has an inline-SVG
  illustration (`src/components/site/FeatureArt.jsx`), wired up through the `Art` field
  in the `FEATURES` array in `Marquee.jsx`. To add a card, add a new art component and a new entry.
- **Physics blocks.** `SERVICES` in `PhysicsSection.jsx` grew from 8 to 18 blocks (WhatsApp Button,
  Google Maps, Contact Forms, Price Lists, Google Reviews, Online Booking, Logo Design,
  Hosting & Domains, Maintenance, Image Carousels). Add/remove blocks there as the portfolio grows.
- **Bug fix — blocks couldn't be dragged on PC.** The old code only enabled dragging when
  `'ontouchstart' in window` was false, which is true on many touch-capable Windows laptops. Dragging is
  now always enabled. Matter's own wheel and touch handlers (which call `preventDefault` and block
  page scroll) are removed; a custom touch handler only captures a gesture when the finger lands on a
  block, so phones can drag blocks and still scroll the page.

  (`mockup-orange`, `mockup-green`, `mockup-purple`, `mockup-lime`,
  `mockup-orange-alt`, `mockup-green-alt`); add more color classes in
  `site.css` if you need more than six cards.
- **Pricing page — hosting note added.** A new pill-styled line ("We provide
  hosting for webpages @ R200 a month...") was added above the existing
  "No hidden fees..." tagline in `src/pages/Pricing.jsx`, styled via
  `.hosting-note` in `site.css`.

  Professional package: R5,500 → R6,000. Enterprise remains "Custom." These
  are plain strings in `src/pages/Pricing.jsx` (`.pricing-price` divs) —
  there's no shared pricing config file, so if prices change again, edit
  them directly in that file.
- **Bug fix — scroll lock on the "Services That Work" physics section.** The
  interactive physics blocks (`src/components/site/PhysicsSection.jsx`, built
  with Matter.js) were capturing the mouse wheel and blocking page scroll
  whenever the cursor was over that section. The code was removing event
  listeners for the legacy `mousewheel`/`DOMMouseScroll` event names, but
  Matter.js's `Mouse` module actually binds its wheel handler (which calls
  `preventDefault()`) to the modern `wheel` event. Fixed by removing the
  listener for the correct event name (`mouse.element.removeEventListener('wheel', mouse.mousewheel)`).
  If a future Matter.js version changes its internal event binding again,
  re-check `node_modules/matter-js/src/core/Mouse.js` for the exact event
  name it attaches to.

## Quick sanity check after any change

Always run `npm run build` and confirm it completes with no errors before
considering a change "done." A broken build means the live site won't update
correctly.
